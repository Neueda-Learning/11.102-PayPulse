### MEM-006 | 2026-07-30 | Idempotent duplicate submission → 200 + existing payment (not 409)
- **Decision:** When a client submits a `POST /payments` with an `idempotencyKey` that already exists, the API returns **`200 OK`** with the existing payment resource (not `201`, not `409`).
- **Rationale:** Smoother client UX/retry-safety — the brief's Considerations section explicitly asks "reject or return existing?" and treats retries as a first-class concern (network retries should be safe/idempotent). Reserving `409 DUPLICATE_PAYMENT` strictly for a stricter interpretation if the instructor requests "reject" behavior instead — trivial one-line change if so.
- **Alternatives Considered:** `409 Conflict` with `DUPLICATE_PAYMENT` error code (brief's Appendix B literally maps this) — kept as a documented alternative; easy to switch. `201` with existing payment (rejected — misleading, implies a new resource was created).
- **Status:** ✅ Accepted (default) — **flag to confirm with instructor**; revert to 409 in 5 minutes if they prefer strict rejection.

### MEM-007 | 2026-07-30 | Expose BOTH auto-progression and explicit transition endpoints
- **Decision:** The system auto-progresses a payment through `CREATED → VALIDATED → SENT → COMPLETED` (or to `FAILED`) automatically/synchronously after creation for demo speed, but we ALSO expose explicit transition endpoints (e.g. `POST /payments/{id}/validate`, `/send`, `/complete`) so transitions can be triggered/tested independently and so the state machine's guard logic is directly demonstrable (good for sequence diagrams + live demo + testing).
- **Rationale:** Best of both worlds — smooth automatic demo flow for the "happy path" story, plus explicit control for testing invalid-transition rejection (Appendix F test scenarios need to *attempt* an illegal transition, which requires an addressable endpoint).
- **Alternatives Considered:** Auto-progression only (rejected — can't easily demo/test "invalid transition rejected" without an endpoint to call it on). Explicit-only, no auto-progression (rejected — every demo/test would need manual multi-step calls, slower to show the full lifecycle).
- **Status:** ✅ Accepted.

### MEM-013 | 2026-07-30 | Idempotency-Key delivered as HTTP header, not request body field
- **Decision:** Clients pass `Idempotency-Key: <string>` as a request header on `POST /payments`, not as a JSON body field.
- **Rationale:** Standard REST/HTTP convention (matches Stripe, PayPal, and other real payment APIs the training project mirrors); keeps the idempotency concern out of the domain payload, and lets the same body be resubmitted unchanged if a client needs to retry with a different key.
- **Alternatives Considered:** Body field `idempotencyKey` (was in the initial SRS draft) — superseded; still supported conceptually (mapped internally the same way) but the API contract now formally uses the header.
- **Status:** ✅ Accepted — supersedes SRS FR-1.1 body-field mention.

### MEM-014 | 2026-07-30 | Explicit transition endpoints return 200 even when the outcome is FAILED
- **Decision:** `POST /payments/{id}/validate|send|complete` return HTTP `200` whenever the transition *operation itself* completes (even if the payment's resulting status is `FAILED`). HTTP error codes (400/404/409/500/503) are reserved strictly for when the API call itself cannot be honored (bad request, illegal transition, not found, conflict, internal fault) — not for "business outcome was a failure."
- **Rationale:** Avoids conflating HTTP transport/request semantics with domain/business outcomes — a very common real-world API design mistake. Frontend can rely on `response.body.status` to know the payment outcome, and HTTP status to know if their *request* was even valid.
- **Alternatives Considered:** Return non-2xx (e.g. 422) whenever the resulting status is FAILED — rejected, muddies the "did my request work" vs "did the payment succeed" distinction and complicates frontend error handling.
- **Status:** ✅ Accepted.

### MEM-016 | 2026-07-30 | Idempotency key clarified: scoped to submission attempt, NOT payment content
- **Decision:** Formally clarified (added FR-1.1a + §7a scenario table to `04-SRS.md`, expanded `11-API-DESIGN.md` §9) that the `Idempotency-Key` is generated **client-side, once per submission attempt**, immediately before the request fires (e.g. `crypto.randomUUID()`) — it is **never derived from payment field values** (amount/accounts/currency). A retried/duplicated *attempt* (double-click, network retry) reuses the same key and is deduplicated; a deliberate, separate payment — even with identical field values — gets a fresh key and is correctly created as a new, independent payment.
- **Rationale:** Team raised a valid concern — if the key were content-derived, a user legitimately paying the same account the same amount twice (e.g. two separate invoices) would be incorrectly blocked as a "duplicate." Scoping the key to the client's request-attempt lifecycle (matching how Stripe/PayPal-style APIs do it) solves the *accidental double-submit/retry* problem the brief actually asks about, without breaking legitimate repeat payments.
- **Alternatives Considered:** Server-derived/content-hash key (amount+accounts+time-window) — rejected, blocks legitimate repeats and is fragile (what time window is "the same" payment?). No idempotency key at all, relying purely on user discipline — rejected, brief explicitly asks us to consider double-submission.
- **Status:** ✅ Accepted.

### MEM-020 | 2026-07-31 | Scale target ~40,000 req/min → API rate limiting (token bucket)
- **Decision:** Design and budget for a peak of **~40,000 requests/minute** (≈667 req/sec) system-wide. Introduce a **rate-limiting filter** at the API boundary using a **token-bucket algorithm** (library: **Bucket4j**, in-memory for Sprint 1, Redis-backed bucket for horizontal-scale correctness in Sprint 2+). Limits are enforced per logical client (IP or `Idempotency-Key`/API-key-shaped header if present) AND a global system-wide ceiling as a backstop. Breaching the limit returns `429 Too Many Requests` + `RATE_LIMIT_EXCEEDED` error code + `Retry-After` and `X-RateLimit-*` headers.
- **Rationale:** Customer explicitly asked "we have 40k hits on api per minute, rate limit... how we implement rate limitation." Token bucket is simple to reason about/demo, allows short bursts (better UX than a strict fixed window), and Bucket4j is a lightweight, dependency-light Java library that doesn't require infrastructure changes for Sprint 1.
- **Alternatives Considered:** Fixed-window counter (rejected — allows a burst at window boundaries, more prone to thundering-herd); Sliding-log (rejected — memory-expensive at this volume); Leaky bucket (rejected — smooths but doesn't allow legitimate bursts as gracefully as token bucket for a payments UI's "submit" pattern); doing rate limiting only at an infra/gateway layer (nginx/API Gateway) — kept as a **complementary, not alternative** layer (defense-in-depth, see MEM-022); noted as a production recommendation but not required for the training deliverable.
- **Status:** ✅ Accepted.

### MEM-021 | 2026-07-31 | Concurrency & durability strategy for scale
- **Decision:** Beyond the existing `@Version` optimistic-locking (NFR-8), formally adopt: (1) **stateless service layer** so instances can scale horizontally behind a load balancer; (2) **tuned HikariCP connection pool** sized for concurrent DB access (avoid pool starvation under burst load); (3) **DB indexes** on `idempotency_key` (already unique), `status`, `created_at`, and `source_account_id` to keep list/filter/analytics queries fast under load; (4) the **existing idempotent-receiver pattern (MEM-006/007)** as the primary defense against duplicate-submission races, now explicitly re-validated against the higher-concurrency target; (5) **Resilience4j Circuit Breaker + Retry** around the simulated send/complete steps so a burst of simulated downstream failures degrades gracefully (fail fast) instead of exhausting threads; (6) durability of the audit trail is preserved by keeping the status-update + history-insert in the **same DB transaction** (already MEM-008/010) — this does not change, it's simply re-confirmed as non-negotiable at scale.
- **Rationale:** Customer explicitly asked "how we handle concurrent users and corresponding implementation" and stressed **durability and reliability** alongside speed. These are additive, low-risk hardening steps on top of decisions already made (MEM-008–010), not a redesign.
- **Alternatives Considered:** Pessimistic row locking (rejected — unnecessary contention/latency cost for this access pattern, optimistic locking + retry is sufficient and lower-latency); full async/queue-based processing (Kafka/RabbitMQ) for send/complete (noted as a natural Sprint 3/production evolution — richer durability story — but deferred: adds infra dependency risk under a 7-day deadline; current synchronous-with-circuit-breaker approach meets the requirement without it).
- **Status:** ✅ Accepted.

### MEM-022 | 2026-07-31 | API security hardening (without introducing a full auth system)
- **Decision:** Even though there is still no login/session system, apply the following security controls: (1) **strict Bean Validation + parameterized queries** (JPA/Hibernate already prevents SQL injection by construction — reconfirmed, no native/concatenated queries allowed); (2) **HTTPS-only** in any deployed environment (local dev may use HTTP); (3) **secure response headers** (`Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, restrictive `Content-Security-Policy` on the React app, locked-down CORS allow-list rather than `*`); (4) **rate limiting** doubles as a DoS/brute-force mitigation (MEM-020); (5) **generic, non-leaking error responses** — `GlobalExceptionHandler` (already MEM-008-adjacent) never serializes stack traces/internal exception messages to the client; (6) **request payload size limits** (reject oversized bodies early) to blunt payload-based DoS; (7) **dependency vulnerability scanning** (OWASP Dependency-Check or `npm audit`/`mvn versions` as a CI step, stretch); (8) **least-privilege DB credentials** (app's MySQL user has only the grants it needs — no `DROP`/`GRANT`); (9) **sensitive-value masking in logs** (account numbers partially masked, e.g. `ACC1000****`, in application logs).
- **Rationale:** Customer explicitly asked "how we secure API from attack and vulnerabilities." These controls are the practical, high-value subset achievable without building a full authentication/authorization system (explicitly still out of scope per the brief) — they address OWASP-API-Top-10-style concerns (injection, broken object-level access is N/A with single-user, security misconfiguration, insufficient rate limiting) proportionate to a training project.
- **Alternatives Considered:** Full OAuth2/JWT auth layer (rejected — explicitly out of scope, brief says single user/no auth, would be scope creep); doing nothing beyond input validation (rejected — customer explicitly asked for attack/vulnerability hardening, so at minimum headers + rate limiting + no-leak errors are warranted).
- **Status:** ✅ Accepted.

### MEM-025 | 2026-08-05 | Notifications (#21) — wire existing module into payment lifecycle via Observer, not direct calls

### MEM-026 | 2026-08-05 | Notification recipient identity — new `owner_email`/`owner_name` columns on `account`
- **Decision:** `Account` gains two new **nullable** columns: `owner_email`, `owner_name` (Flyway `V6__add_account_owner_contact.sql`). The recipient of a payment's lifecycle emails is resolved from the payment's **source account's** owner contact fields. If either is null (e.g. legacy seeded accounts), the listener logs a warning and **skips sending** rather than failing the payment (notifications are best-effort, never allowed to affect payment processing — see MEM-025 async decision).
- **Rationale:** The system remains single-operator/no-auth (MEM-005/A-1), but an operator can own multiple accounts (MEM-017) and a real notification needs *somewhere* to send to. Modeling contact info at the `Account` level (rather than a new `User`/`Customer` entity, which would reopen the "do we need auth" question) is the smallest correct addition — consistent with "start small" and not scope-creeping into #24 (Full Auth, explicitly deferred).
- **Alternatives Considered:** A single global `application.yml` config value (`paypulse.notifications.operator-email`) — rejected as the primary mechanism because it can't express "which of my several accounts should notify which inbox" (a legitimate real-world case even for one operator, e.g. personal vs. business email per account); kept as an optional fallback default (`paypulse.notifications.default-recipient-email`) for accounts with no `owner_email` set, so demos never silently produce zero emails. A new `User`/`Customer` table (rejected — reopens auth/ownership scope explicitly deferred to #24).
- **Status:** ✅ Accepted.

### MEM-027 | 2026-08-05 | Dashboard SSE replaces 30-second polling
- **Decision:** `GET /analytics/stream` (Server-Sent Events, `text/event-stream`) is added, backed by a Spring `SseEmitter` registry in a new `analytics/service/DashboardStreamService`. On every payment status transition (again via the existing `PaymentStatusChangedEvent`, MEM-025 pattern) the service recomputes the affected KPI deltas (or, simplest correct implementation: recomputes and pushes the full `KpiSummaryResponse`, debounced/coalesced — e.g. max 1 push per 2 seconds even under burst load) to all connected emitters. The frontend (`frontend/index.html`) replaces its `setInterval(loadDashboard, 30000)` with an `EventSource` connection, falling back to the existing 30s poll **only** if `EventSource` is unavailable/the connection drops repeatedly (graceful degradation, not a hard requirement on SSE support).
- **Rationale:** Directly answers the customer's implicit ask for a "live" dashboard — SSE is the right tool here (not WebSockets) because the data flow is strictly **server→client, one-directional, text-based, auto-reconnecting via native browser `EventSource`** — exactly SSE's sweet spot, with far less protocol/infra ceremony than WebSockets for a one-way feed. Debouncing/coalescing pushes protects against the ~40k req/min-scale event volume (NFR-10) turning into an SSE flood.
- **Alternatives Considered:** WebSockets (rejected — bidirectional channel is unused overhead here, more complex to scale/load-balance with sticky sessions); shortening the poll interval instead of SSE (rejected — doesn't remove wasted requests during idle periods, doesn't meet the explicit "no 30s poll" directive); long-polling (rejected — SSE achieves the same "push" feel with simpler server code and native reconnect).
- **Status:** ✅ Accepted.

### MEM-029 | 2026-08-05 | Payment Cancellation (#18) — new terminal `CANCELLED` status, reachable only from `CREATED`
- **Decision:** Add `CANCELLED` as a new terminal `PaymentStatus` enum value. The **only** legal transition into it is `CREATED → CANCELLED` (client-initiated, via `POST /payments/{id}/cancel`), before the automatic `validate()` step has run. Once a payment has progressed to `VALIDATED`/`SENT`/`COMPLETED`/`FAILED`, cancellation is no longer possible (`409 Conflict` + `INVALID_STATUS_TRANSITION`-family error, new code `PAYMENT_NOT_CANCELLABLE`). Implemented as a new `CancelledState` class (same `PaymentState` interface, MEM-009) — kept consistent with the existing State Pattern rather than a special-cased `if` in the service layer.
- **Rationale:** Matches the feature definition exactly ("Cancel a payment while it's still in `CREATED` status, before it's processed" — `chirag/01-feature-list.md` #18). Because Core's auto-progression (MEM-007) resolves `CREATED→VALIDATED` **synchronously and immediately**, there is a genuinely narrow window for cancellation to matter in the current synchronous design — flagged explicitly as an open question for the instructor (see `12-CLARIFICATION-QUESTIONS.md` new Q15) about whether auto-progression should gain a small artificial delay in V2 specifically to make cancellation a meaningful, demoable feature (today it would almost always race-lose against the synchronous engine). Default until answered: keep auto-progression synchronous, document cancellation as "protects against any future async/queued processing model," and demo it via the explicit `/validate` control endpoint (MEM-007) to force a `CREATED`-only window.
- **Alternatives Considered:** Allowing cancellation from `VALIDATED`/`SENT` too (rejected — feature spec explicitly scopes it to pre-processing, and undoing a `SENT` payment is really "reversal" territory, #19, not "cancellation"). Modeling cancellation as a flag on `Payment` instead of a state (rejected — inconsistent with the existing, working State Pattern and would require special-casing every state's guard logic).
- **Status:** ✅ Accepted, with one flagged open question (see above).

### MEM-030 | 2026-08-05 | Payment Reversal (#19) — new linked payment, NOT a state transition on the original
- **Decision:** `POST /payments/{id}/reverse` is only legal for a `COMPLETED` payment. It does **not** transition the original payment's status (it remains `COMPLETED` — the historical record of what happened is never rewritten, consistent with NFR-2 auditability). Instead: (1) the original payment gets a new **`reversed` boolean flag** (default `false`) set to `true`, plus a `reversal_payment_id` FK column pointing to the new payment; (2) a **brand-new** `Payment` row is created with `reversal_of_payment_id` pointing back to the original, `sourceAccountId`/`destinationAccount` swapped (the reversal flows money the opposite direction), same `amount`/`currency`, and goes through the **normal** `CREATED→VALIDATED→SENT→COMPLETED/FAILED` lifecycle like any other payment. A `COMPLETED` payment that is already `reversed=true` cannot be reversed again (`409` + new code `PAYMENT_ALREADY_REVERSED`).
- **Rationale:** Matches the feature definition exactly ("Reverse a completed payment by creating a new, offsetting payment" — `chirag/01-feature-list.md` #19) and is how real payment systems (and double-entry bookkeeping generally) model reversals — never mutate/delete the original record, always add an offsetting transaction. Reusing the existing state machine/validators/audit trail for the new reversal payment means zero new business-rule code is needed for the reversal's own lifecycle — only the "create a linked, direction-swapped payment" orchestration step is new.
- **Alternatives Considered:** Adding a `REVERSED` terminal state directly on the original payment (rejected — would either violate the "no backwards/rewriting" principle of the state machine, MEM-009/`10-UML-STATE-DIAGRAM.md`, or require `COMPLETED` to gain an outgoing transition, contradicting its documented terminal-state design note). Allowing reversal of `FAILED` payments (rejected — nothing to reverse, no funds ever moved).
- **Status:** ✅ Accepted.

### MEM-031 | 2026-08-05 | Multi-Currency Conversion (#20) — display-only FX, no real ledger conversion
- **Decision:** `GET /fx/rate?from=INR&to=USD` (and reverse) is added, backed by a new `FxRateService` using a **static, config-driven** rate table (`application.yml`, e.g. `paypulse.fx.rates.INR-USD: 0.012`) — **not** a live third-party rate feed. This is used **only** for **display purposes** on the frontend (e.g. "this ₹250 payment is roughly ~$3.00" shown as a secondary/greyed-out hint) — it does **not** change how a payment is created, validated, or settled. A payment's `currency` still must equal its source account's currency exactly (MEM-018 unchanged) — no cross-currency payment is ever actually executed.
- **Rationale:** Feature #20 is explicitly listed as **Future/post-MVP** in `chirag/01-feature-list.md` ("Allow paying out of one currency's account into another currency, with a live/looked-up exchange rate") — a full FX ledger-conversion feature is a genuinely large scope addition (live rate feed integration, rounding/precision rules, FX-loss accounting, reconciliation) inappropriate to fully build in this V2 wave. Shipping the **display-only** subset gives real, demoable customer value (the visual "what would this be in the other currency" affordance) without the ledger-integrity risk of moving real money across a conversion boundary on a static/stale rate.
- **Alternatives Considered:** Full conversion support allowing a source-INR-account payment to settle into a USD destination (rejected for this wave — see rationale; explicitly flagged as a follow-up in `12-CLARIFICATION-QUESTIONS.md` new Q16 for the instructor to confirm appetite for the larger scope). Live third-party FX API integration (rejected for now — external dependency risk/cost not justified for a training project's display-only need; static config rates are trivially upgradable to a live provider later behind the same `FxRateService` interface, Strategy pattern).
- **Status:** ✅ Accepted (display-only scope) — full conversion remains Future/out-of-scope pending instructor confirmation.

### MEM-032 | 2026-08-05 | CSV Export (#14) — synchronous streamed export, same filters as list, capped row count
- **Decision:** `GET /payments/export` (same query params as `GET /payments` — `status`, `search`, `sourceAccountId`, `sort` — but **no pagination**, since a filtered full-result export is the point) streams `text/csv` directly from the existing `PaymentRepository` query methods (via a `Stream<Payment>`/cursor-based read, not "load everything into a `List` in memory first") to avoid an OOM risk on a large filtered set. A hard cap (`paypulse.export.max-rows`, default 50,000) is enforced — a request whose filter would exceed it returns `400` + new code `EXPORT_TOO_LARGE` with guidance to narrow the filter, rather than silently truncating the file (silent truncation of a financial export is a correctness/trust risk).
- **Rationale:** Matches feature #14 exactly ("Download the current filtered payment list as a CSV file"). Streaming (not buffering) is the correct, industrial approach for any potentially-large tabular export — same principle already applied to pagination (NFR-7) is extended here.
- **Alternatives Considered:** Client-side CSV generation from already-fetched paginated JSON (rejected — only exports the *current page*, not the full filtered set, defeating the feature's purpose). Async export-then-download-link pattern (job queue + polling) — noted as the natural evolution if row counts grow far beyond the cap, but rejected as unnecessary complexity for this wave given the cap.
- **Status:** ✅ Accepted.
