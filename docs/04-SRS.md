## 1. Purpose

Define the functional and non-functional requirements for the **Payments Processing REST API** and its **React frontend**, so that backend and frontend can be designed and built in parallel with a shared, unambiguous contract.

## 2. Actors

| Actor | Description |
|---|---|
| **Client / End User** | The single (unauthenticated) user interacting via the React UI or directly via the REST API. |
| **System (self)** | The backend itself acts as an internal actor that simulates payment network processing (async/scheduled transition from `SENT` → `COMPLETED`/`FAILED`). |
| **Instructor ("Customer")** | Provides/clarifies requirements on request; not a system actor. |

## 3. Functional Requirements

### FR-1 — Create Payment
- **FR-1.1** Client can submit a new payment with: `sourceAccount`, `destinationAccount`, `amount`, `currency`, optional `reference/description`, and an optional `idempotencyKey` (delivered as an `Idempotency-Key` HTTP header per MEM-013, not a body field).
- **FR-1.2** On creation, payment status is set to `CREATED` and a status-history record is written.
- **FR-1.3** If an `idempotencyKey` is supplied and a payment with that key already exists, the system **returns the existing payment** (HTTP `200`, per MEM-006) rather than creating a duplicate.
- **FR-1.4** Request is validated per FR-9 (Validation Rules) **before** persisting as `CREATED`...

  > **Design decision:** invalid input (a) is rejected outright with `400` and nothing persisted for basic field-level validation (missing/malformed fields). (b) Business-rule validation (unknown account format, unsupported currency) is persisted first as `CREATED` then immediately transitioned to `FAILED` with an audit trail entry — so there's a real audit trail of *why* it failed.

- **FR-1.5 — Idempotency Key Semantics (clarified, see §3.1 below for full detail):** The idempotency key identifies a **single client submission attempt**, NOT the business content of the payment. It is generated **client-side**, once per attempt, immediately before the HTTP request is sent — never derived from/hashed against `amount`/`sourceAccount`/`destinationAccount`. This means:
  - A genuine retry of the *same* attempt (network timeout, double-click before the UI disables the button) reuses the *same* key → correctly deduplicated, no second payment created.
  - A deliberate, separate payment — even with **byte-for-byte identical field values** (e.g. paying the same account the same amount again next week, or twice in a row on purpose) — uses a **newly generated key** → correctly creates a new, independent payment. The system has no way (nor should it) to distinguish "duplicate by accident" from "legitimately identical business transaction" other than via this client-attempt-scoped key.

### FR-1.1a — Idempotency Key — Full Design Detail

**Where does the key come from?** Generated by the **client** (React frontend, or any API caller) — e.g. `crypto.randomUUID()` in the browser — NOT generated or derived by the server, and NOT computed from payment field values.

**Why not derive it from payment content (e.g. hash of amount+accounts+day)?** Because that would silently block legitimate repeat payments that happen to share the same fields (a very real case: recurring rent, subscription-style manual payments, or simply paying the same supplier the same amount twice in one day on purpose). The brief's own Considerations section frames this as "detect duplicates" from a **submission/network** perspective (accidental double-submit), not a **business** perspective (intentionally identical payments) — so the key must be scoped to the *request attempt*, not the *payload*.

**Lifecycle (client-side):**
1. User fills the Create Payment form.
2. On Submit click, frontend generates ONE key for this attempt and immediately disables the Submit button (prevents double-click from generating two keys).
3. Key is sent as the `Idempotency-Key` header with the request.
4. If the request fails transiently (network error/timeout) and the frontend retries automatically or the user clicks "Retry" on the same failed attempt → **same key is resent**.
5. On success, or on a final non-retryable failure (e.g. validation error the user must fix), the key is discarded. Any subsequent submission (even of the identical form data) generates a **new** key.

**Server-side handling (belt-and-braces, see `05-ARCHITECTURE.md` / `06-DESIGN-PATTERNS.md` #7):**
1. `IdempotencyService.findExisting(key)` — application-level lookup **before** insert. If found → short-circuit, return existing payment (`200`).
2. `idempotency_key` column has a **DB-level `UNIQUE` constraint** as a safety net for the race condition where two requests with the same key arrive near-simultaneously (e.g. a genuine network retry firing while the first attempt's response is still in flight) — if the app-level check misses the race, the DB constraint violation is caught and translated into the same "return existing payment" response, rather than surfacing a raw 500/constraint-violation error to the client.
3. If **no key is supplied at all**, no deduplication is attempted for that request — it always creates a new payment (see A-5). We *recommend* (frontend does this by default) always sending a key, but the API doesn't mandate it, since not every caller (e.g. a quick manual `curl`/Swagger test) needs duplicate protection.

**What the key does NOT do:** it does not prevent a user from legitimately sending "the same payment" (same accounts/amount) multiple times as separate business transactions — each such deliberate submission simply gets its own key and becomes its own independent payment record. This is by design and matches how real payment APIs (Stripe, PayPal, etc.) implement idempotency keys.



### FR-2 — Validate Payment (system-driven transition: `CREATED → VALIDATED` or `→ FAILED`)
- **FR-2.1** System runs validation rules (Appendix C of brief — amount, account, currency) against a `CREATED` payment.
- **FR-2.2** On success → status `VALIDATED`, audit entry recorded.
- **FR-2.3** On failure → status `FAILED`, with `errorCode` + human-readable message, audit entry recorded.
- **FR-2.4** For the core/demo build, validation is triggered **synchronously immediately after creation** (simplest, deterministic, easy to demo). Design as a distinct step/service method so it *could* become async later without an API shape change.

### FR-3 — Send Payment (system-driven transition: `VALIDATED → SENT` or `→ FAILED`)
- **FR-3.1** A `VALIDATED` payment is transitioned to `SENT`, simulating transmission to a destination system (no real network call — brief explicitly says simulate).
- **FR-3.2** Simulated failures (configurable random/deterministic failure injection) may occur here, moving to `FAILED` with a `NETWORK_ERROR` or `PROCESSING_ERROR` code — this is what demonstrates the "any stage can fail" + retry/error-handling story.

### FR-4 — Complete Payment (system-driven transition: `SENT → COMPLETED` or `→ FAILED`)
- **FR-4.1** A `SENT` payment is transitioned to `COMPLETED` after a simulated processing delay/step.
- **FR-4.2** On simulated failure → `FAILED` with appropriate error code.

### FR-5 — Retrieve Payment
- **FR-5.1** Client can `GET` a single payment by ID, returning current status + all core fields.
- **FR-5.2** 404 with `PAYMENT_NOT_FOUND` if it doesn't exist.

### FR-6 — Retrieve Payment History (Audit Trail)
- **FR-6.1** Client can `GET` the full status-transition history for a given payment ID, ordered chronologically, each entry showing: previous status, new status, timestamp, triggered-by (`SYSTEM` since no auth), and error code/message if applicable.

### FR-7 — List / Search / Filter Payments
- **FR-7.1** Client can list all payments, paginated.
- **FR-7.2** Client can filter by `status`.
- **FR-7.3** Client can search by payment ID or reference/description (per Appendix D UI ideas).

### FR-8 — Error Detail for Failed Payments
- **FR-8.1** When a payment is `FAILED`, the payment resource (and/or its history) exposes `errorCode` + `errorMessage` so the frontend can render it (Appendix B codes).

### FR-9 — Validation Rules (Appendix C, finalized for our system)
- Amount: `> 0`, `<= 1,000,000`, max 2 decimal places.
- Source/destination accounts: required, must differ from each other, must match a defined format (regex, e.g. alphanumeric 8–20 chars), must "exist" — for this training system, accounts are **not a separately managed entity**; we validate **format only** (documented assumption — see §7 Assumptions) unless instructor says otherwise.
- Currency: must be one of a supported ISO 4217 subset, e.g. `USD, EUR, GBP` (configurable list).
- Idempotency key: optional, if provided must be unique per payment.

### FR-10 — Status Transition Rules (state machine — Appendix C)
Valid transitions ONLY:
```
CREATED    → VALIDATED
CREATED    → FAILED
VALIDATED  → SENT
VALIDATED  → FAILED
SENT       → COMPLETED
SENT       → FAILED
```
Any other transition attempt (including from a terminal state `COMPLETED`/`FAILED`) is rejected with `INVALID_STATUS_TRANSITION` (400). **No transition ever goes "backwards."** `COMPLETED` and `FAILED` are terminal.

## 4. Non-Functional Requirements (NFRs)

| ID | Requirement |
|---|---|
| NFR-1 | **Idempotency** — duplicate submissions (same idempotency key) never create a second payment record. |
| NFR-2 | **Auditability** — every status change is persisted (append-only), never overwritten/deleted. |
| NFR-3 | **Consistency** — status transitions are validated server-side regardless of what the client requests; invalid transitions are always rejected, never silently accepted. |
| NFR-4 | **API documentation** — Swagger/OpenAPI available and kept in sync with actual endpoints. |
| NFR-5 | **Testability** — business logic (validation, state transitions) must be unit-testable independent of the web layer and DB (per Appendix G guidance). |
| NFR-6 | **Consistent error contract** — all errors return a predictable JSON shape `{errorCode, message, timestamp, ...}` with correct HTTP status per Appendix B mapping. |
| NFR-7 | **Performance (light)** — no specific SLA required for a training project, but list/search endpoints must be paginated (avoid unbounded result sets). |
| NFR-8 | **Concurrency (basic)** — two simultaneous status-transition requests on the same payment must not corrupt state (DB-level optimistic locking `@Version` — minimum viable protection; full concurrency handling is a stretch item per Appendix E). |
| NFR-9 | **Portability** — runs against MySQL via Spring Data JPA; tests can run against H2 without code changes (dialect-only config difference). |

## 7. Assumptions

- **A-1:** Single user, no auth — confirmed by brief; `triggered_by` in audit trail will always read `SYSTEM` (or `CLIENT` for the initial creation) rather than a real username.
- **A-2:** No separate `Account`/`Customer` master entity in the core build — accounts are free-text identifiers validated by format/pattern only, not existence-checked against a real ledger. (Flag to revisit with instructor if they expect account existence checks.)
- **A-3:** "Sent to destination system" and "processing/confirmation" are **simulated** — e.g. an internal service call with an artificial delay and a configurable success/failure rate — no real payment gateway integration (explicit in brief).
- **A-4:** Validation (`CREATED→VALIDATED`) happens synchronously right after creation in the core build, not via an external queue — keeps Sprint 1 scope small; can evolve into async processing (Appendix E-adjacent) later.
- **A-5:** Idempotency key, if omitted by the client, means no duplicate protection is requested for that call — each such request creates a new payment. (We recommend the frontend always generates one, but the API doesn't mandate it.) **The key is scoped to a single client submission attempt (generated fresh per attempt, client-side), never derived from payment field values — see FR-1.1a for full rationale and the scenario table below.**
- **A-6:** Currency support list is small and hardcoded/config-driven initially (e.g. USD, EUR, GBP) — not a full ISO 4217 table.
- **A-7:** MySQL is used per team's VM/tooling (MEM-003); schema managed via Flyway migrations, inspected/administered via MySQL Workbench.

## 7a. Idempotency — Worked Scenarios (disambiguates FR-1.5 / FR-1.1a)

| # | Scenario | Client behavior | Key reused or new? | Server outcome |
|---|---|---|---|---|
| 1 | User clicks Submit once, response arrives normally | Generates 1 key, sends once | N/A (single send) | New payment created, `201` |
| 2 | User double-clicks Submit before button disables | Ideally UI prevents this; if it slips through, both requests carry the key generated at the *first* click (button disable is synchronous with key generation) | **Same key** | Second request finds existing payment → `200`, no duplicate row |
| 3 | Request times out client-side, frontend auto-retries | Retry re-sends the in-flight attempt | **Same key** | If original actually succeeded server-side, retry returns existing payment (`200`); if original never reached server, retry creates it (`201`) |
| 4 | User submits, payment completes, then 5 minutes later submits the *exact same form values again* on purpose | Treated as a brand-new attempt | **New key** | A second, independent payment is created — **this is correct behavior**, not a bug |
| 5 | No `Idempotency-Key` header sent at all (e.g. raw `curl`/Swagger test) | N/A | No key | Always creates a new payment; no dedup attempted (A-5) |
| 6 | Two near-simultaneous requests with the same key hit the server at almost the same instant (race) | N/A | Same key | App-level check may miss the race; DB `UNIQUE` constraint on `idempotency_key` catches it — violation is translated to "return existing payment" rather than a raw error |

## 9. Acceptance Criteria (Sprint 1 / Core "Definition of Done")

- [ ] Can create a payment via API with minimal valid fields → returns `201` with `CREATED` status + Location header/ID.
- [ ] Submitting the same idempotency key twice does **not** create a duplicate row; returns the original payment.
- [ ] Invalid amount/currency/account submission is rejected with correct `errorCode` + `400`.
- [ ] A newly created payment automatically progresses to `VALIDATED` (or `FAILED` with reason) without manual client intervention.
- [ ] A `VALIDATED` payment can be progressed to `SENT` then `COMPLETED` (or `FAILED` at either stage), each transition recorded in history.
- [ ] `GET /payments/{id}` returns current state; `GET /payments/{id}/history` returns full ordered audit trail.
- [ ] Attempting an illegal transition (e.g. force `COMPLETED → CREATED` if such an endpoint existed) is rejected with `INVALID_STATUS_TRANSITION`.
- [ ] `GET /payments?status=FAILED` (or similar) filters correctly.
- [ ] Swagger UI reachable and reflects all of the above.
- [ ] Unit tests cover: validation rules, state machine transitions (valid + invalid), idempotency logic.
