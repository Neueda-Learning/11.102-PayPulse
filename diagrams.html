Payment State Machine

All valid payment states, the transitions between them, and terminal states. No transition ever goes backwards.

FAILED is reachable from CREATED (validate() fails), VALIDATED (send() fails — NETWORK_ERROR), and SENT (complete() fails — PROCESSING_ERROR). Any illegal transition attempt throws InvalidStatusTransitionException → 400.

Open Questions

For the instructor / customer check-in. Each has a working default assumption so development is not blocked. Log every answer in 02-MEMORY.md.

High priority — affects core design Medium priority — affects scope or UX Lower priority — good default in place
Q 01  High

Duplicate idempotency key — return the existing payment with 200 OK, or reject with 409 Conflict + DUPLICATE_PAYMENT?

Default

Return 200 + existing payment (MEM-006). Brief Appendix B lists DUPLICATE_PAYMENT → 409, but the Considerations section frames it as an open question.

Why it matters

Changes the API contract and frontend retry logic. Needs confirmation early.

Q 02  High

Auto-progression vs. explicit lifecycle — auto-progress CREATED → VALIDATED → SENT → COMPLETED, or require an explicit API call per transition?

Default

Both — auto-progress for the main demo flow, and also expose explicit /validate, /send, /complete endpoints (MEM-007).

Why it matters

Affects demo realism and how much of the retry / error-handling story is visible during the presentation.

Q 03  High

Account existence validation — must accounts exist in a registry table, or is format-only validation (regex) sufficient?

Default

Format-only — no separate Account entity in core scope (SRS A-2).

Why it matters

If real account existence is required, we need a seed accounts table and an INVALID_ACCOUNT check path — best decided early.

Q 04  Medium

Processing speed — should the lifecycle complete instantly (synchronous), or with a visible step-by-step delay?

Default

Synchronous / instant for Sprint 1. Artificial delay + polling can be added in Sprint 2 for demo realism.

Why it matters

Determines whether the frontend needs polling / websockets or a single request-response cycle.

Q 05  Medium

Supported currencies — small fixed list (USD, EUR, GBP), a custom list, or full ISO 4217?

Default

Small hardcoded list: USD, EUR, GBP (SRS A-6). Easy to extend.

Q 06  Medium

Failure simulation — deterministic triggers (reserved test account always fails), random chance, or both?

Default

Deterministic triggers for reliable demo (reserved account always fails) + small random chance for realism.

Why it matters

Deterministic triggers make failure scenarios reproducible during the live presentation.

Q 07  Medium

Search — partial/case-insensitive match on reference, or exact match only?

Default

Partial, case-insensitive match on reference; exact match on id (UUID).

Q 08  Lower

Preferred stretch feature if core finishes early — cancellation, analytics, concurrency demo, or other?

Why it matters

Guides Sprint 3 work in the final 1–2 days rather than guessing.

Q 09  Lower

Presentation focus — mostly product demo, mostly technical deep-dive, or an equal mix?

Why it matters

Shapes how we structure the live demo and how long we spend on architecture vs. user journey walkthrough.
