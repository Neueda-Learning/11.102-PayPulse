❓ Clarification Questions
Open questions for the instructor / customer. Each shows the working default assumption and why it matters. Bring to the next check-in and log answers in 02-MEMORY.md.

Q1 🔴

Idempotent duplicate submission — if a client submits the same Idempotency-Key twice, should we (a) return the existing payment with 200 OK, or (b) reject with 409 Conflict + DUPLICATE_PAYMENT?

Default

Option (a) — return 200 + existing payment (MEM-006). Brief Appendix B lists DUPLICATE_PAYMENT → 409, but the Considerations section asks the question explicitly — ambiguous by design.

Why it matters

Changes the API contract and frontend retry logic. Needs early confirmation to avoid a retrofit.

Q2 🔴

Auto-progression vs. explicit lifecycle — should a payment auto-progress CREATED → VALIDATED → SENT → COMPLETED immediately after creation, or require an explicit API call per transition?

Default

Both — auto-progress for the main demo flow, and also expose explicit /validate, /send, /complete endpoints for testing and manual control (MEM-007).

Why it matters

Affects demo realism and how much of the retry/error-handling story is visible to the user during the presentation.

Q3 🔴

Account existence validation — must source/destination accounts exist in a registry table, or is format-only validation (regex) sufficient?

Default

Format-only — no separate Account entity in core scope (SRS A-2).

Why it matters

If real account existence is required, we need a seed accounts table and an INVALID_ACCOUNT check path — a data-model change best made early.

Q4 🟡

Realistic delay vs. instant — should validation/processing simulate a visible delay, or resolve synchronously within the same HTTP request?

Default

Synchronous/instant for Sprint 1; can add artificial delay + polling in Sprint 2 for demo realism.

Why it matters

Determines whether the frontend needs polling / websockets or just a single request-response cycle.

Q5 🟡

Supported currencies — is a small hardcoded list (USD, EUR, GBP) sufficient, or do you expect a broader ISO 4217 configurable set?

Default

Small hardcoded/config-driven list (SRS A-6).

Q6 🟡

Failure simulation strategy — random (10% chance), deterministic triggers (magic account/amount), or configurable via an admin endpoint?

Default

Deterministic triggers for reliable test/demo (a reserved test account always fails) PLUS a small random chance for realism — gives both reliable test cases and a live-demo surprise element.

Q7 🟡

Search behavior — exact-match or partial/fuzzy match on reference? Case-sensitive?

Default

Partial, case-insensitive match on reference; exact match on id (UUID).

Q8 🟢

Pagination defaults — any preference on default page size or sort order for the payment list?

Default

size=20, sorted by createdAt DESC (newest first).

Q9 🟢

Which Appendix E advanced feature would most impress? (concurrency demo, reporting/analytics, payment cancellation, or other)

Why it matters

Helps prioritize Sprint 3 stretch work in the final 1-2 days rather than guessing.

Q10 🟢

Presentation emphasis — technical (design patterns / architecture) or product-demo style (user-facing flow), given the audience may include non-technical stakeholders?

Why it matters

Shapes how we structure the live demo and any slides accompanying it.
