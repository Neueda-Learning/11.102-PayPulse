Project Overview

A plain-language summary of what PayPulse is, how a payment moves through the system, and what the end user experiences.

PayPulse is a payment management system where a user submits a payment — amount, currency, source and destination accounts — and the system automatically validates it, sends it for processing, and confirms completion. Every step is permanently recorded in an audit trail. The user can track status, view history, filter and search payments, and see exactly what went wrong if a payment fails.

What the user sees — three screens

ScreenWhat the user can do
Create Payment Enter source account, destination account, amount, currency, and an optional description, then submit. The system processes it immediately and displays the final status.
Payment Details View the current status of any payment, all its fields, and the complete timestamped history of every stage it went through — including error details if it failed.
Payment List Browse all payments with pagination, filter by status (e.g. show only FAILED), and search by payment ID or reference text.

Key safeguards built in from day one

SafeguardWhat it means in plain English
Duplicate protection If the user accidentally clicks Submit twice, or the network retries the request automatically, the system will not create two payments. It detects the repeat and safely returns the original.
Full audit trail Every status change is permanently recorded with a timestamp. Nothing is ever overwritten — the complete history of what happened to any payment is always available.
Validation before processing The system checks the amount, currency, and account format before attempting to send. Invalid payments are rejected immediately with a clear reason.
Strict lifecycle A payment can never skip steps or go backwards. A completed payment cannot be re-validated; a failed payment cannot be silently retried. The lifecycle is fully enforced.

Payment — field-by-field explanation

FieldWhat it holdsRequired?Example
id A unique identifier generated automatically by the system for every payment. Auto-generated a3f2c1d0-…
amount The money value to transfer. Must be greater than zero, maximum 1,000,000, and no more than 2 decimal places. Yes 250.00
currency The 3-letter currency code. Only a supported list is accepted (USD, EUR, GBP by default — see Open Questions Q4). Yes GBP
source_account The account the money is coming from. Must follow the expected format (alphanumeric, 8–20 characters). Yes ACC00123456
destination_account The account the money is going to. Must follow the same format and cannot be the same as source. Yes ACC00789012
reference An optional free-text note or label (e.g. invoice number, reason for payment). Optional Invoice #2024-09
status The payment's current position in its lifecycle. Automatically set and updated by the system. Auto-set COMPLETED
error_code & error_message Only populated when status is FAILED. Contains a short code (e.g. INVALID_CURRENCY) and a human-readable explanation. On failure only INVALID_CURRENCY
idempotency_key A unique ID sent by the client to prevent accidental duplicate payments. If omitted, no duplicate detection is applied for that request. Optional uuid-abc-123

Q 01
Must answer Affects: account validation, data model

Should the system verify that accounts actually exist, or only check that they are in the correct format?

Our assumption

We currently check format only — e.g. alphanumeric, 8–20 characters. We do not verify that an account exists in any registry or database. This is simpler and faster to build.

If you want existence checks

We would need to build an Account entity — a list of valid accounts the system checks against. This adds a few extra hours of work and may require a seed-data setup or a new management screen. We would need to know today to plan it into the schedule.

Options

A. Format-only validation — simpler, faster (our default)
B. Existence check against a fixed list of known test accounts — moderate effort
C. Full Account entity with management screen — significant additional scope

Q 02
Must answer Affects: user experience, API behaviour

When a user accidentally submits the same payment twice — double-click or network retry — should the system return the original silently, or show a clear duplicate error?

Our assumption

We silently return the original payment with a success response. The retry is invisible to the user — seamless and safe. This matches how Stripe and PayPal handle duplicate submissions.

If you want an explicit error

We return a 409 Conflict response with a DUPLICATE_PAYMENT error code. The user sees an explicit message. This is a one-line change — just confirm your preference early.

Options

A. Silent return — smooth, retry-safe (our default)
B. 409 error — explicit, user-visible rejection

Q 03
Must answer Affects: demo experience, frontend design

After submitting, should the user see the final result immediately, or watch it progress step by step with a short visible delay?

Our assumption

The result appears immediately. The full lifecycle completes in under a second and the final status is shown straight away. Simpler, more reliable, and easier to test.

If you want step-by-step visibility

We can add a short delay (e.g. 1–2 seconds per stage) so the status updates on screen in real time: CREATED → VALIDATED → SENT → COMPLETED. More engaging for a live demo but adds complexity. We would do this in the second half of the project if time allows.

Options

A. Instant result — simple, reliable (our default)
B. Step-by-step with visible progress — more engaging for the presentation demo

Q 05
Important Affects: how failure scenarios appear in the demo

When should a payment fail during simulated processing — on specific test data, randomly, or both?

Our assumption

Deterministic triggers — specific reserved account numbers always cause a failure (NETWORK_ERROR or PROCESSING_ERROR), making failure scenarios reliable and repeatable for demo and testing. We may also add a small random chance for additional realism.

Why this matters

If you want to demonstrate a failed payment during the live presentation, a deterministic trigger means it always fails on cue. A purely random failure may not occur at the right moment.

Options

A. Deterministic: a reserved test account always triggers failure (our default)
B. Random: each payment has a small independent chance of failing
C. Both: deterministic triggers plus a small random chance
